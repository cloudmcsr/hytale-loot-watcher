8 · What z means — and why a correct predictor makes a bell curve

z is not an error rate — it is the error measured in units of “how much error pure randomness would naturally produce”:

z = (empirical − predicted) / σ,    σ = √( p·(1−p) / N )

  • empirical = how often the leaf actually fired in the simulation; predicted = what loot_chance.js claims; σ = the expected size of the random wobble for N batches (for a 5% leaf over 20,000 batches, σ ≈ 0.15 pp).
  • Even a perfect prediction never matches exactly. A leaf predicted at 5% should fire ~1000 times in 20,000 batches — you'll observe 987, or 1014, or 1003. That's dice behaving like dice, not a bug: flip a fair coin 100 times and you almost never get exactly 50 heads.
  • So the comparison is not “did we hit the number exactly” (impossible), it is “is the deviation the size chance would produce, or bigger?” z ≈ 0 → normal random size; z ≈ 2 → happens to ~5% of leaves by luck; |z| > 3 → ~0.27% by luck; |z| > 4 → ~0.006% — many of those would mean the prediction is actually wrong.
  • The bell curve IS what “correct” looks like. The yellow overlay in graph 1 is the N(0,1) distribution chance produces when predictions are right. If every z were exactly 0 that would be a red flag — real randomness is never that clean; it would mean the simulation is not actually random (or the “empirical” side was computed from the prediction instead of generated).
  • Why flat-zero tables exist (graph 3): 477 of 662 tables contain only guaranteed 100% drops. Their outcome is identical every batch (σ = 0), so z = 0 is genuinely correct — there is nothing random in them to deviate. The statistical test only has teeth on the ~185 tables with real randomness.
  • The pp error rate is reported separately (section 7): mean absolute error 0.118 pp / worst single leaf 1.065 pp = plain accuracy; z = statistical correctness of the model. Two views of the same comparison.

Methodology

  • Semantics — server-source verified (Batch Q): root Weight dead data, absent Weight = 100, Choice share w/sum + uniform K, Multiple independent gate w >= rnd*100, fastRound count, Droplist visited-set, qty uniform + amount>0.
  • Setup — every loot table/drop (662 unique after de-duplicating the 50 loot_table_definitions against drops) is annotated by loot_chance.js, then run through loot_generator.js, a faithful port of the decompiled server's populateDrops chain: mulberry32 seeded per table: (0xC0FFEE ^ imul(ti+1, 2654435761)) >>> 0.
  • Test — per leaf: empirical fire rate p̂ vs predicted p over 20000 batches; z = (p̂−p)/√(p(1−p)/N). Leaves with expected fires < 5 are skipped (28 leaves). A leaf whose σ = 0 at p = 1 (and an empirical 0/1 tie) is scored z = 0 by exact match.
  • Empty leaves — Empty containers manifest as a “#nothing” event, so the viewer-side “#nothing” chance is verified like any other leaf (1 sampled in graph 4).
  • Known artifacts — near-certain leaves (p ≥ 70%) quantize z toward 0 (sd = 0.17 in that bin), slightly suppressing the global sd (0.90) and the 1–2σ tail bars. Bulk bins (<70%) all show sd between 0.99 and 1.07.
  • Coverage note — quantity ranges that include 0 (e.g. stick 0–2) can legally produce no item server-side; predictions describe the node's fire chance, which is what the simulation tests.
